# 2026.269.2248 — feat(service)!: own the typed-step kind + materialization (C7)

## Summary

C7 crutch-sweep, producer-first leg 3/5. Adopt `sdk` `v0.2026269.2222` (which adopts
`spec#177`, `v0.2026269.2150`): the `service` verb candy now **owns both halves** of its typed
install-step lowering, so charly core holds no per-kind switch.

Before this PR the candy returned a neutral `kit.StepDescriptor` + a candy-local
`kit.StepKindName`, and charly's `check_kit_adapter.go` mapped the kind
(`kitStepKindToCharly`) and rebuilt the real step (`materializeStep`) — a kernel kind switch,
an incomplete seam by the boundary law. Now the candy implements the widened
`checkstep.StepProvider`:

```go
func (verb) StepKind() spec.StepKind { return spec.StepKindServicePackaged }

func (verb) MaterializeStep(op *spec.Op, runAsUser, candyName, _ string, _ []string) spec.InstallStep {
	var in params.ServiceInput
	kit.DecodeInput(op.PluginInput, &in)
	return &spec.ServicePackagedStep{
		Unit:        in.Service,
		TargetScope: spec.OpStepScope(runAsUser),
		Enable:      true,
		CandyName:   candyName,
	}
}
```

The load-bearing `Reverse()` (disable / restore-enabled / remove-dropin) stays on the built
step (package main) — the candy owns only the construction. `ConstructStepDescriptor` and the
descriptor types are gone; `TestServiceVerb_StepProvider` now asserts the real
`*spec.ServicePackagedStep`, including the run-as → scope threading (`1000` → user, `0` →
system) and the candy name.

Also adds the missing `InvokeProvider` method to the test `fakeCC` — the newer SDK's
`CheckContext` requires it, and the pin bump surfaces the latent test staleness (R2, fixed
here).
